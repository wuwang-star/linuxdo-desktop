# 设置中心 UI（参考 FluxDO/ALDR）

## Goal

独立设置中心（/settings）收拢全部设置项，信息架构对齐参考项目的分类结构（FluxDO：外观/偏好/网络/通知/数据/日志/关于；ALDR：模式/图像/主题/网络/交互/过滤器等域），分类骨架完整、每类有真实内容或诚实占位。

## Background（已确认事实）

- 调研见 research.md。用户 2026-10-16 二次强调：「参考项目在设置页面会有各种分类的」——分类数量与结构须向两系统看齐，不能只塞现有两项。
- 现有可归置的真实设置：translate、DoH（实验）、原生通知（p2a 已实现但**无开关**——缺口）、请求诊断日志（diag:list，100 条环，现仍在 LoginView）。
- App 顶栏已有设置入口；路由 /settings 与 SettingsView 已落地（首轮：网络/翻译/关于 三分类）。

## Requirements

- **R1 分类结构（7 类）**：外观、阅读、通知、网络、翻译、日志、关于——左导航对齐参考项目风格。
- **R2 通知分类（真实新设置）**：原生通知开关 `notificationEnabled`（默认开），settings.ts 持久化 + IPC（settings:getNotification/setNotification）+ `notify.ts` 发送前检查 + UI toggle。参考 FluxDO 通知设置行为。
- **R3 日志分类（迁移）**：LoginView 请求诊断卡整体迁入，展示 diag 列表（时间/方法/URL/状态/耗时），行为不变；登录页随之瘦身。
- **R4 网络/翻译分类**：首轮已迁移，保持行为不变。
- **R5 外观/阅读分类（诚实占位）**：各放一张说明卡——外观「主题系统规划中」、阅读「全局阅读偏好规划中（当前仅楼内 per-topic 开关）」，不放假开关。
- **R6 关于分类**：应用名+版本+文档指针（首轮已落地）。

## Acceptance Criteria

- [x] **AC1** `/settings` 直达（未登录亦可）、顶栏入口可达、LoginView 不再承载设置表单（首轮已验证 typecheck/smoke）
- [ ] **AC2** 通知开关：关 → MessageBus push 不再弹系统通知（进程内徽标/toast 不受影响）；开 → 恢复；重启后保持。（代码链路已落地：settings 持久化→IPC→notify.ts 发送前检查→UI toggle；真机 push 验证待人工）
- [ ] **AC3** 日志分类展示诊断列表，与迁移前 LoginView 一致；登录页无诊断卡。（代码迁移完成且补全时间/方法列；页面渲染待人工）
- [ ] **AC4** 七分类全部可见可切换；外观/阅读为说明占位卡，无假控件。（代码完成；页面渲染待人工）
- [x] **AC5** `pnpm run typecheck` 0 错误；`pnpm run smoke` SMOKE_OK。（2026-10-16 实测通过）
- [ ] **AC6** 设置页呈现 tokens 化视觉：卡片行结构统一、开关/分段选择组件化、间距字阶一致；DoH 组明显优于迁移前的裸表单。（tokens+组件已落地，视觉效果待人工确认）

- **R7 设计语言基线（用户 2026-10-16：「框架定了，设计呢」）**：styles.css 顶部建立 CSS 变量 tokens（色彩/间距/圆角/字阶），表单组件化——开关用 switch 样式、模式用分段选择、设置项用「标签行+控件行」卡片行结构；设置中心整体作为设计基准页，DoH 组重点重做（现状过于简陋）。不引入 UI 框架，纯 CSS 演进。
